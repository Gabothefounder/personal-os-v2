# Agentic PMF Engine

Status: synthesis v0.1 — operating doctrine, not software

Inputs:

- `intelligence/research/agentic-business-operating-practices-2026-08-31.md`
- `wisdom/lenses/NAVAL.md`
- `wisdom/lenses/FRANKLIN.md`
- `projects/scanscam/EXPERIMENTS.md`
- `projects/scanscam/CUSTOMER_INTEL.md`
- `thesis/TRUST_THESIS.md`

Purpose: use agents to reduce the latency and cost of finding product-market fit **without** confusing agent activity, shipped pages, or generated ideas with market evidence.

This synthesis does not claim ScanScam has PMF and does not select a product wedge.

---

## Core doctrine

> Agents compress execution around evidence. They do not replace the market.

> The human owns the game, the exposure, the relationships, the money, and the final judgment.

> No new agent without a recurring job. No new business box without a falsifiable market test.

---

# 1. Naval lens

## Game

The attractive game is not “operate lots of tiny AI businesses.” That would reward novelty and reset compounding.

The potentially worthwhile long game is the broader trust/verification territory **if** repeated market contact increasingly clarifies a valuable wedge.

Agents should reduce the cost of exploring adjacent trust problems while preserving accumulated experiment history, customer language, relationships, and technical assets.

**Naval warning:** horizontal PMF search can become industry-switching in miniature. If every experiment targets unrelated buyers, channels, and jobs, the system creates motion but resets specific knowledge.

### Rule

Prefer a **productive pivot** that carries forward at least one meaningful asset:

- customer relationship
- distribution
- domain knowledge
- outcome data
- reputation
- workflow
- reusable infrastructure

A box that resets all six needs unusually strong evidence before entering.

## Specific knowledge

Agent building itself is rapidly commoditizing. Prompting, scraping, landing-page production, research synthesis, and first-draft outreach are weak moats.

The PMF engine should discover what becomes specific knowledge through real work:

- where customers actually hesitate
- what evidence changes a decision
- what trust failures cost
- who owns the problem internally
- which edge cases generic models miss
- which relationships provide privileged access
- which outcomes are hard to observe publicly

**OPEN:** founder-market fit is not yet proven. The engine should collect evidence of where Gabriel gets unusual access, credibility, response, judgment advantage, or energy instead of assuming it.

## Ownership

If this system works, the valuable owned residue should not be the agent prompts.

Seek ownership of:

- customer relationships
- experiment/outcome history
- proprietary correction/failure data
- brand/reputation
- distribution
- workflows that become embedded
- eventually product/IP/equity

If agents only make someone else’s platform more useful while leaving no residue, leverage is high but ownership is weak.

## Leverage

Agents are cheap labor and parallel cognition. Use them for tasks where marginal agent work replaces meaningful founder hours **and remains checkable**.

High-leverage candidates:

- broad public research
- source comparison
- experiment preparation
- data summarization
- code/page drafts
- instrumentation checks
- structured follow-up drafts
- experiment postmortems
- memory/ledger maintenance

Keep human attention for:

- choosing the problem
- reading emotional/strategic customer signal
- negotiation
- reputation-bearing communication
- allocating capital
- committing to a market
- exceptions where evidence is weak

## Judgment

The PMF engine increases the number of possible bets. That makes judgment more important, not less.

Approval gates should sit at:

- external messaging
- ad spend
- pricing/discounting
- publication under Gabriel/ScanScam name
- production changes with material risk
- legal/compliance claims
- money movement
- promises to customers

The agent can recommend. The owner decides.

## Compounding

Every completed experiment should leave residue in the system:

**hypothesis → customer/payer → channel → offer → exposure → behavior → money → outcome → learning**

Compounding fails when:

- results remain in a platform dashboard
- conversations are not logged
- a page is replaced before the result is written
- metrics change definition between tests
- a new test ignores prior negative evidence

The ScanScam reconstruction showed these failures already. The engine exists partly to prevent recurrence.

## Build + sell

Do not sell “AI-powered trust intelligence” unless a customer independently values the outcome.

Sell the actual job:

- prevent a costly mistake
- verify a counterparty before exposure
- reduce fraud loss
- resolve a suspicious transaction
- shorten a decision
- provide evidence/recourse

If the offer requires explaining why agents are impressive, the market pull is probably weak.

## Future

This is a legitimate way to live inside the agentic future: agents are used on real business work with real consequences, rather than only discussed.

But “future” is not a moat. The system should ask after every experiment:

> If models become 10× better and cheaper, which part of this opportunity becomes more valuable?

Good answers may include distribution, private outcomes, accountability, permissions, identity, guarantees, relationships, trust, and transaction access.

Bad answer: “our prompt is better.”

## Freedom / good life

The agent system fails if Gabriel becomes full-time manager of a digital bureaucracy.

### Constraint

Do not add an agent unless:

- the job recurs
- it saves more review/execution time than it creates in maintenance
- its output affects a real decision or workflow
- its owner can understand how to stop it

No agent zoo.

# 2. Franklin lens

## Utility

Start from the repeating nuisance, not from agent capability.

A valid PMF question is:

> What concrete trust-related nuisance happens often enough, costs enough, and is unresolved enough that someone acts or pays?

Examples are hypotheses only. The nuisance must come from evidence.

Agentic cleverness without a user is Franklin’s whistle.

## Experiment

Franklin pushes strongly toward a smaller system than the phrase “Business in a Box” suggests.

First prove the operating loop with one real experiment:

1. evidence gathered
2. hypothesis written
3. threshold declared
4. market artifact created
5. real people exposed
6. outcome measured
7. errata recorded

Then copy what works.

Do not build a company-generating machine before one agent-assisted experiment clearly beats the manual process.

## Practicality

Use tools already in reach before adding infrastructure.

Current assets can already support most of v0:

- GitHub workspace = canonical written memory
- ChatGPT/web = research and analysis
- Cursor = code/file execution
- Vercel = deployment/runtime observation
- existing ScanScam code = experiment surface

Only add databases/orchestration/agent frameworks when a repeated bottleneck proves they are needed.

## Reputation

Automated external communication creates a direct attack surface on credit/reputation.

Franklin’s wheelbarrow principle translates cleanly:

- agents may prepare industry
- the founder must ensure the visible result is actually good

No autonomous cold outreach, public posting, customer promises, or trust verdicts in v0.

If later delegated, external actions need narrow templates, logs, sampling, and easy shutdown.

## Network

Agents should strengthen human relationships, not replace the conversations that produce specific knowledge.

For PMF, the highest-value network output is often:

- a real customer conversation
- a referral
- a design partner
- a trusted introduction
- repeated access to a domain

An agent that saves Gabriel from all contact may destroy the source of learning.

## Institution

Repeated success may eventually justify an institution: a stable workflow, product, standard, dataset, or network.

But institution comes **after** repeated utility.

Franklin sequence:

local defect → small prototype → measure → copy → institutionalize

Not:

architecture → roster → agent hierarchy → search for a reason to use it

## Distribution

A validated insight should be turned into reusable distribution:

- targeted outreach patterns
- content grounded in field evidence
- search pages around validated intent
- partner/referral channels
- product loops

Distribution is allowed to compound; unsupported claims are not.

## Independence

Own the memory and the decisions even if models/vendors change.

The durable record should remain portable:

- markdown/git
- explicit experiment schemas
- source links
- outcome data
- customer language
- decision history

Vendor-specific bots are replaceable. Institutional memory should not be.

## Discipline

Run a small number of experiments concurrently.

Every experiment must close before becoming forgotten infrastructure:

- result
- what it falsified
- what it did not falsify
- next decision

Every agent must have a maintenance review and a kill condition.

Curiosity is allowed in research; execution needs order.

## Revision / errata

Every confident system claim should have a path to correction.

If an agent:

- repeats stale sources
- overstates evidence
- creates rework
- misses a critical exception
- costs more than it saves

record the miss, change one thing when possible, rerun the failed case plus prior passing cases, and downgrade/retire the agent if it does not improve.

### Shared conclusion

The correct object is not a “team of AI employees.”

It is a **small, evidence-bearing operating system** that lets the founder run more real experiments without throwing away compounding knowledge or reputation.

- preserve compounding
- seek ownership
- use agents as leverage
- protect judgment and freedom

# 4. PMF evidence ladder

The engine should weight evidence rather than count experiments equally.

## Level 5 — strongest

- actual payment at meaningful price
- signed contract / committed budget
- repeat paid use
- retention / repeated behavior
- expansion / referral driven by value

## Level 4

- qualified design partner commits time/data/workflow access
- customer changes an existing process to use the solution
- strong recurring usage with clear value even before monetization

## Level 3

- meaningful cold outreach response
- booked conversation from qualified buyer
- explicit budget/process pain confirmed with specific existing spend
- customer provides real case/data to solve

## Level 2

- signup / waitlist
- CTA click
- completed free scan
- email capture
- stated willingness to pay

## Level 1 — weakest

- founder intuition
- AI recommendation
- desk research
- simulated customer
- page deployed
- impressions
- generic enthusiasm

A large amount of Level 1–2 evidence does not automatically equal Level 4–5 evidence.

# 5. Agent-shaped-work gate

Before assigning any PMF task to AI, ask:

### Size
Is the work substantial enough to justify delegated cognition?

### Independence
Can it be handed off without constant founder intervention?

### Separation
Would a distinct researcher/critic perspective materially improve the result?

### Checkability
Can the output be verified much faster/cheaper than producing it?

### Economic value
Does delegating this task free founder time for customer, judgment, selling, relationships, or another scarce activity?

Verdict:

- tiny/open thinking → CHAT
- bounded multi-step → ONE AGENT
- broad/decomposable + cheap verification → MULTI-AGENT
- judgment-heavy / uncheckable / low-value → HUMAN or DO NOTHING

# 7. Autonomy ladder

An agent earns permission rather than receiving “full autonomy.”

### A0 — advise
Read + analyze only.

### A1 — draft
Create artifacts for human review.

### A2 — reversible internal action
Update a non-critical draft/workspace with audit trail.

### A3 — system-of-record action
Write structured data where rollback/history exists; sampled review required.

### A4 — external action
Send/publish/contact within approved narrow policy; strong monitoring and escalation.

### A5 — consequential authority
Money, contracts, irreversible production changes, legal claims, destructive operations.

**Default for PMF v0: A0–A1.**

A4–A5 remain human-controlled unless a later workflow develops strong evidence, deterministic limits, auditability, and explicit approval.

# 8. Proposed ScanScam v0 roles — NOT IMPLEMENTATION YET

Do not create these merely because they have names. First verify the jobs recur.

## 1. Evidence Scout

Job: produce a sourced weekly/on-demand brief of new evidence relevant to one approved PMF question.

Authority: A0.

Definition of done: evidence, counterevidence, source quality, unknowns, and one concise implication; no business recommendation without labeling inference.

## 2. Experiment Designer

Job: convert one founder-approved problem/segment into a falsifiable experiment spec.

Authority: A1.

Definition of done: payer, trigger, assumption, artifact, channel, cost, sample/exposure target, success threshold, kill threshold, evidence level.

## 3. Evaluator / Archivist

Job: compare observed outcome to predeclared criteria and prepare the evidence update.

Authority: A1 initially; proposed repository write only after review.

Definition of done: fact/inference split, result, falsified/not-falsified, next decision, proposed updates to experiment/customer-intel files.

## Human owner

Gabriel retains:

- selection of problem/market
- customer interviews
- price and negotiation judgment
- approval of outreach/content
- capital allocation
- reputational commitments
- final BUILD / TEST / WATCH / KILL decision

# 9. What not to build yet

- autonomous outbound swarm
- autonomous ad-spend optimizer
- agent marketplace
- persistent “CEO agent” making product decisions
- ten departmental bots
- complex multi-agent orchestration
- standalone agent database/control plane
- agent-generated PMF scores
- automatic product pivots

These may become rational only after repeated workflows create enough volume and review burden to justify them.

---

# 10. Success criteria for the PMF engine itself

The PMF engine is useful only if it improves the founder’s real operating throughput.

Possible metrics:

- time from question → real market test
- percentage of experiments with predeclared success/kill criteria
- percentage with result logged within 24h of closure
- number of qualified customer conversations per founder hour
- amount of founder time shifted from research/admin to customers/judgment
- review/rework time per agent output
- repeated agent error rate
- experiments accidentally repeated unchanged
- revenue / design-partner / retention evidence generated

The engine should be killed or simplified if agent maintenance consumes more high-value founder time than it returns.
